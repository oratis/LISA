## 1. 用户反馈的两个问题

### 为什么 Coding Plans 找不到 Codex？

**这台 Mac 已有 Codex CLI，而且已经通过 ChatGPT 登录。LISA 没有找到它的程序位置。**

实际程序：

```text
/Applications/ChatGPT.app/Contents/Resources/codex-cli/CodexCLI.app/Contents/MacOS/codex
```

本机 `--version` 返回 `codex-cli 0.166.0-alpha.6`，`login status` 返回 `Logged in using ChatGPT`。这是 CLI 的登录状态查询，没有读取或复制凭据内容。[OpenAI 官方认证说明](https://learn.chatgpt.com/docs/auth)也将 `codex login status` 列为诊断方式。

安装版 `/api/plans` 同时返回：

```json
{"id":"codex","available":false,"loggedIn":true,"mark":"✗"}
```

原因有两层：

1. LISA 从 Mac App 启动时的 PATH 不包含上面的应用内目录；`detectCodex()` 只查 `codex` 或显式覆盖路径，没有像 Claude 那样做应用包发现。
2. 即便设置 `LISA_PTY_CODEX_CMD` 让检测通过，`run_on_plan → launchAgent → buildDispatchArgv` 仍固定启动 `codex exec`，忽略检测得到的实际路径。隔离实验已复现“检测 available=true，但启动报 codex not found on PATH”。因此，只改界面或只补覆盖变量不能解决完整调用链。

另外，检测器只检查路径存在，不检查是否为可执行文件；一个权限为 0600 的普通文本文件也会被判断为“已安装”。

**建议修复：**把程序发现、可执行校验、登录诊断和真正启动统一使用同一个解析结果；支持本机 ChatGPT/Codex 应用包路径及用户指定路径。界面分别显示“未找到程序”“未登录”“可运行”，提供重新检测入口。修复验收必须包含从 Mac App 发起一次真实 Codex 任务。

源码：`src/model/plans.ts:62、89、175`；`src/tools/run_on_plan.ts:118`；`src/tools/dispatch_agent.ts:61、106`。

### 为什么 Chat → Skills 是空的？

**安装版的 LISA 技能目录确实为空，而 Codex 的技能不会自动导入。**

- 安装版 `/api/skills` 返回 `{"skills":[]}`。
- `~/.lisa/skills` 中可见的技能文件数为 0。
- `~/.codex/skills` 顶层用户技能目录有 14 个 `SKILL.md`；此数不包含所有系统技能、插件技能。
- 空列表界面有文字提示，但没有导入、创建或说明技能来源的直接入口。

还存在一处实际不一致：模型提示词使用 `discoverSkills(projectRoot)`，可发现项目 `.lisa/skills` 和 `.agents/skills`；Skills API 与技能工具的 list 操作却只用个人目录 `listSkills()`。实验结果：

| 临时目录内容 | 模型侧发现结果 | Skills 列表结果 |
|---|---|---|
| 仅项目技能 `audit-project` | 1 个 | 0 个 |
| 再增加个人技能 `audit-home` | 2 个 | 1 个 |

在测试实例加入合法的个人技能后，面板立即显示其名称和描述，说明列表渲染本身能工作。

**建议修复：**统一模型、API 和面板的技能发现规则；标明个人／项目来源；给空状态增加“创建技能”“导入已有技能”。从其他工具导入时，应先展示可导入项和实际兼容范围，避免默默复制所有技能。

源码：`src/paths.ts:52`；`src/skills/discovery.ts`；`src/skills/tool.ts:54`；`src/web/server.ts:4295`；`src/web/assets/client/main.js:1682`。

### E02：Mac 构建失败的具体位置

```text
packaging/mac-client/Sources/Lisa/BackendController.swift:151:37
'weak' ownership of capture 'self' differs from implicitly-captured
strong reference in outer scope [ImplicitStrongCapture]
```

外层 `kill.terminationHandler` 隐式强捕获 self，内层 `Task { @MainActor [weak self] ... }` 被当前编译器拒绝，项目又把警告视为错误。建议明确两层闭包的捕获关系，随后重跑完整 `swift test` 和 App 打包。23 项独立安装逻辑测试通过不能替代这个发布检查。

### E04：错误响应复现

在隔离代理中让指定接口返回 HTTP 503、JSON `{"error":"Audit injected service unavailable"}`：

| 面板 | 实际显示 | 正确行为应为 |
|---|---|---|
| Skills | 保留 `loading…`；全局提示 `Cannot read properties of undefined (reading 'length')` | 清楚的加载失败提示和重试按钮 |
| Tools | 保留 `loading…`；全局提示 `Cannot read properties of undefined (reading 'map')` | 同上 |
| Memory | USER.md、MEMORY.md 都显示 `(empty)`，即使临时磁盘上已有记忆 | 显示加载失败，不能暗示记忆不存在 |

恢复接口后，重新打开 Memory 能显示原有测试内容；这次复现没有发生数据丢失。根因是这些面板未检查 `response.ok`，且对返回数据缺少校验和局部错误处理。

本地截图：Skills 接口失败后仍停在 loading（保存在本机测试证据目录，未上传）。

### 7 项主程序失败的归因

- `src/web/lisa-client.test.ts`：4 项 `sessionLabel` 测试在提取函数的独立上下文中缺少 `sessionNames`。浏览器里的右键重命名、持久化和跨窗口同步测试通过；这 4 项不等于 4 个真实重命名故障。
- 同一文件：1 项“无残留 CJK 文案”断言发现 GitHub 模块硬编码中文，是实际国际化不一致。
- `src/web/lisa-html-snapshot.test.ts`：2 项仍假设旧的前端文件集合与一对一导出。新增 GitHub CSS／JS 拼接后约定发生变化，需要更新有意义的断言。
- 唯一跳过项：真实 PTY `cat` 回环。原生 `pty.node` 无法加载；不能把跳过视为通过。

E07 与 E01 是不同调用路径：Coding Plans 的 `run_on_plan` 使用子进程委派；交互式 Control PTY 使用 node-pty。补 node-pty 并不能修好 Coding Plans 的路径问题。

## 6. 修复与下一轮验收顺序

1. **先完成 Codex 真实调用链。**统一程序解析和启动，增加不存在／不可执行／已安装未登录等状态测试；在 Mac App 的实际启动环境中运行一个临时目录里的无副作用任务，核对结果与错误回显。
2. **恢复 Mac 可构建。**修复捕获问题，完整原生测试与打包通过后再更新安装版。
3. **统一 Skills。**模型、技能工具和 UI 共享技能来源；实现明确的来源展示及创建／导入入口；加入“仅有项目技能”的浏览器回归。
4. **补全失败态。**Skills、Tools、Memory 统一检查状态码、校验结果、展示错误与重试；把本次 503 复现纳入持续回归。
5. **恢复回归检查。**修复 6 项测试上下文／快照约定，GitHub 文案接入语言表；重新跑完整套件。
6. **补真实外部验收。**单独完成 Codex／Claude 真实执行、实体手机配对、语音、邮件、GitHub、MCP、推送及云端账号／计费测试。需要真实账号或会产生外部动作的步骤，应使用明确的测试账号与测试对象。
